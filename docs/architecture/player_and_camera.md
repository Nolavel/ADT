# Player, camera and stance

The player node's two movement modes, the per-mode camera components, transport,
and the stance/aiming state the rest of the game reads.

Split out of `CLAUDE.md` on 2026-08-25 — it had grown to 94 KB with single
paragraphs over 4000 characters, which is a document nobody edits: agents append
to the end instead of correcting the middle, and that is where the repeated drift
came from. The text here is the same text, moved, not rewritten.

`CLAUDE.md` remains authoritative for the rules; this file is authoritative for
the contracts it describes.

---

### Player (`player/player.gd` + `player/player_components/`)

`player.gd` (on `CharacterBody3D`) owns physics, animation state machine, and rotation directly (not delegated to components) for both movement modes it supports:
- **Click-to-move / navigation** (the `ISOMETRIC` default, **and in TPS whenever a scripted path is in flight** — see `_has_scripted_path()`) — driven by `NavigationComponent`, path following in `_handle_navigation`. Currently a straight-line stub: `nav_component.tscn` leaves `navigation_region_path` unset, so `_initialize_navigation()` finds no `NavigationRegion3D` and forces `use_navigation` to `false` at runtime — `set_target_position()` then just emits a single-point path straight to the destination. No obstacle avoidance and no path validation yet. **This is why anything that walks the character somewhere needs a timeout** — a straight line into geometry never arrives and never ends; `InteractComponent.approach_timeout` is that, not defensive padding.
- **Which of the two runs is no longer decided by view mode alone.** A *scripted* path — one set through `move_to_position()` rather than by WASD — takes over in TPS as well, because an auto-approach has to work in both views and `move_to_position()` in TPS used to set a path nothing ever consumed. Two consequences live in `_physics_process()`: `_update_direct_move_target_speed()` is **skipped** while such a path runs (it zeroes `target_speed` whenever there is no WASD input, which would drain the approach's speed before it moved a metre), and a non-zero `_direct_move_direction` **cancels** the path on the spot — the player's own input always wins, and the `movement_stopped` that follows is how `InteractComponent` learns the approach is over. No `Input` is read for that: `TPSMovementSystem` already caches the value every physics frame.
- **Direct WASD movement** (`TPS` view mode) — `TPSMovementSystem` (a `WORLD_SYSTEM_SCRIPTS` entry) feeds `set_direct_move_input()` every physics frame; `player.gd` does the actual velocity/rotation/animation in `_apply_direct_movement`.

Which path runs is gated on `PlayerState.view_mode` inside `_physics_process`. `player_components/` contains three implemented components: `nav_component`, `stamina_component`, `interact_component`. Empty placeholder directories for unstarted components (health, hunger, sleep, wallet, progression, crafting, save) were removed on 2026-07-29; that scope is recorded in `docs/planned_scope.md`. `equipment_component` and `equipment_visuals_component` were implemented later as H5 (2026-08-23).

### Camera (`camera/`)

`camera_follow.gd` is the host; per-mode behavior lives in `camera_component/`: `on_foot_camera_component` (ISOMETRIC orbital + TPS, with three sub-state helpers — `TpsShoulderCameraState` for left/right shoulder offset, `TpsCombatCameraState` for Explore↔Locked lock-on, and `IsometricCameraState` for the ISOMETRIC follow point *and* the ISOMETRIC yaw: dead zone, lead toward the click-to-move destination, a bounded bias toward the ground point under the cursor, a separate vertical channel, asymmetric damping, and an **octant yaw** — the camera faces one of eight fixed compass headings 45° apart rather than continuously chasing the character. Two calls per frame, in order: `update_orientation()`, then the host copies `get_cam_forward()`/`get_cam_right()` into the `Frame`, then `update()`; the dead zone is measured in the camera plane, so advancing the follow point against last frame's basis while the yaw moved this frame slides it sideways. A heading change commits a turn only after clearing the octant boundary by `snap_hysteresis_deg` **and** holding the new answer for `snap_dwell` — *unless* the player has ordered a move to somewhere behind the camera, which `_try_destination_reversal()` answers immediately from `Frame.move_target`, bypassing both gates and the standing-still gate. Two witnesses, deliberately: the body heading is right for "where is this character going" and wrong for "what did the player just decide", and with click-to-move the destination is known a whole turn-and-accelerate before the heading agrees with it. It is also what the gates get wrong on a reversal — a body swinging through 180° passes through every intermediate octant, each a plausible candidate. Only bearings past `reversal_threshold_deg` (112.5°, i.e. `SNAP_STEP * 2.5`, the boundary between the octants in front of the camera and those behind it) qualify; it cannot re-fire, since committing puts the bearing inside the threshold by construction, and the turn itself is a duration-scaled ease, not exponential damping — damping never arrives, and a view that is always turning slightly is one the player cannot use as a frame of reference. **Standing still never rotates the camera at all**, which is what the previous continuous-follow version got wrong. `IsometricCameraDebugOverlay` visualizes the zones when attached), `hover_camera_component` (renamed from `vehicle_hover_camera_component`; `HoverView` = CHASE/COCKPIT), `tube_transit_camera_component` (stub, freelook only), `camera_shake_component` (additive-only, pure getter — cannot leave a residual offset by construction). `camera_follow.gd` also owns an internal `CameraState{GAME, MENU_PAUSE}` for the menu tween, separate from `PlayerState.Mode`. Reads input exclusively through `InputSystems` query methods, not `Input.*` directly. TPS vertical look range (`OnFootCameraComponent.tps_pitch_min_deg`/`tps_pitch_max_deg`, default `-70`/`+60`), the ISOMETRIC dead zone (`IsometricCameraState.dead_zone_x`/`dead_zone_y`, default `0.05`/`0.03`, fractions of viewport size) and the octant turn gates (`snap_hysteresis_deg` `12.0`, `snap_dwell` `0.3`, `snap_turn_duration` `0.25` — the duration for *one* octant; `_turn_duration_for()` scales it by `sqrt(step / 45°)`, so a 180° reversal takes 0.5 s rather than whip-panning at 720°/s, and then by `_turn_soften_for()` — `turn_soften_front` (1.25) across the **front** half of the circle, none across the **back** half, one octant of blend between. The two halves answer different questions and get opposite answers: in front the camera is *following* and a correction that announces itself is what reads as rough, behind it is *reorienting* and the move must land as a decision. Measured — 45° 0.317 s at 212°/s, 90° 0.450 s at 323°/s, 135° 0.433 s at 536°/s, 180° 0.500 s at 675°/s; duration is deliberately **not** monotonic in the step, since 90° covers its angle far more slowly than 135° covers its own; the curve is a trapezoid in angular *velocity* with smootherstep corners, `_turn_ease()`, shaped by `TURN_RAMP_SMALL`/`TURN_RAMP_LARGE` — velocity ramps up over that fraction of the duration, holds a plateau, ramps down over the same fraction at the far end. Because the area is fixed the plateau is `1/(1-ramp)` times the average, so a *smaller* ramp means a flatter, slower peak. That fixed area is the point: at a given duration and angle the average speed is already decided and every curve's peak is at least the average, so "less aggressive" can only mean *lower peak*, i.e. flatter — a higher-order ease has softer ends and a **higher** peak, the opposite of what a small turn wants. `TURN_RAMP_LARGE` is the value at which the profile matches the plain smootherstep it replaced, so a reversal is unchanged. Measured peak angular speed at unchanged durations: 45° 265°/s (was 337), 90° 403 (was 477), 135° 536 (was 584), 180° 675 (was 675) — and the ease-out cubic before *that* opened a 45° turn at 505°/s in its first frame) are `@export` feel values, not implementation constants — tune them in place rather than in code, same convention `TpsCombatCameraState`'s spring constants already follow.

**Stamina is drawn in the world, the cursor only aims.** `StaminaIndicator3D` (`player/player_components/stamina_indicator/`) renders the stamina ring on the ground around the character's feet — arcs whose length is the remaining ratio and whose colour walks full → yellow → orange → red, the two chasing recovery rings, the jump-charge arc and the walk/sprint/no-stamina icons. It owns **no arithmetic**: `StaminaComponent` keeps all of it and this node subscribes. `top_level = true` with the position copied each frame, because the node must follow the player but must **not** inherit their rotation — in COMBAT the body turns to face the camera constantly and a welded ring would swing with every turn. `MouseCursorUI` was where all of this lived until 2026-08-28 and now holds no reference to `StaminaComponent` at all: it says one thing, which is what the player is pointing at — dim grey, brighter over an NPC or item, and `[ ✛ ]` brackets while a firearm is drawn, opening and settling on a spring driven by the **continuous** speed rather than by `is_running`. **In TPS it is pinned to screen centre**, since the mouse is captured there and the camera is what aims. **What is under it is decided by TYPE, not by mask**: the island terrain carries `collision_layer = 3` and so sits on `CHARACTERS` alongside real characters, which no mask can separate — the cursor therefore accepts only `NPCBase`, `InteractableObject` or an interactable's `Area`, which also gives honest occlusion for free, since the ray returns the nearest hit. That terrain layer is still wrong and is not fixed by this.

**Steady-state follow rates are per-view, and ISOMETRIC's must stay near-transparent.** `_update_camera_position()`'s trailing smoothing pass runs at `TPS_FOLLOW_SPEED`/`TPS_LOOK_SMOOTHING` in TPS and `ISO_FOLLOW_SPEED`/`ISO_ROTATION_SPEED` (both `30.0`) in ISOMETRIC, falling back to `view_transition_speed` only while `view_mode_animating`.

**In steady-state ISOMETRIC the position half of that pass is a critically damped spring** (`Smoothing.smooth_damp_vector3()`, `ISO_POSITION_SMOOTH_TIME` `0.08`, velocity carried in `_iso_pos_velocity`), not the exponential. This is a replacement, not an addition — there is still exactly one filter between `IsometricCameraState` and the camera. The reason is order, not rate: an exponential is first-order and passes a step in the *target's velocity* through in the same frame, and the follow point is assembled from piecewise rules (the dead-zone kink, the moving/settling rate switch at `SETTLING_SPEED_THRESHOLD`, a lead that collapses on arrival, a cursor bias that drops out when the ray misses) that are continuous in position and discontinuous in rate of change. Measured against a 50% step in target velocity at `run_speed`: the exponential jerks its own velocity by 3.05 m/s in one frame, the spring by 0.52. The cost is explicit — a spring trails a constant-speed target by `speed * smooth_time`, so 1.24 m at full sprint against the exponential's 0.52 m; that ~0.7 m is constant during a sprint rather than varying, and `LEAD_DISTANCE` absorbs constant framing offsets. **Rotation keeps the exponential in both views** and should stay that way: `_current_yaw` leaves a smootherstep turn already C1 (zero angular velocity at both ends), so there is no velocity step to filter and springing it would only blunt the arrival the octant model exists to produce. ISOMETRIC used to have no branch of its own and fell through to `view_transition_speed` (`4.0`), which put a second time constant behind `IsometricCameraState` — a state whose dead, soft and hard zones are all measured against the follow point it returns, on the assumption that the camera sits there. At `run_speed` 15.5 the two stages together trailed by ~8.3 m, the lead was sized for neither, and the hard zone could not clamp anything because the point it clamped was not the point being drawn. Do not put a second comparable time constant back on this path.

**The spring is an ISOMETRIC-only substitution, and TPS plus both directions of the view transition still ride the exponential.** That `else` branch is load-bearing and was silently lost once (`dae379e`, restored 2026-08-26): with it gone, `camera_current_pos` was written nowhere but inside `if view_mode == ISOMETRIC and not view_mode_animating`, so pressing `V` set `view_mode_animating`, skipped the block, and froze the camera body at its isometric position — through the transition and then through all of TPS, since the mode no longer matched either. Rotation kept lerping on its own line, so it read as "the camera behaves oddly" rather than "the camera is dead". Measured before and after: 0.00 m of travel on the switch versus 7.29 m, ending 10.06 m from the character versus 2.87 m. A regression test that presses `V` and asserts the camera actually travelled is the cheap guard here, because every symptom of this is a feel complaint rather than an error in the log.

The ISOMETRIC dead zone's forward axis is scaled by `Frame.forward_screen_scale` (`sin(|camera_angle|)`, ≈`0.574` at the default `-35°`) before being converted to pixels: the camera looks *down* at the ground, so a metre running away from it covers less screen than a metre running across it. Without that factor `dead_zone_y` behaved as roughly 1.75× its stated value.

**ISOMETRIC aims THROUGH the character, not at them** (`_update_iso_look_ahead()`). At full strength the look target moves `ISO_LOOK_AHEAD_DISTANCE` (2.0 m) forward along the camera's horizontal forward and `ISO_LOOK_TARGET_RAISE` (0.4 m) up, while the camera itself sinks `ISO_CAMERA_DROP` (0.3 m); pitch is then **derived** from camera-to-target and yaw is left to the octant. Strength is `speed_ratio * ISO_LOOK_AHEAD_SPEED_SHARE + cursor_edge_weight * ISO_LOOK_AHEAD_CURSOR_SHARE`, clamped to 1 and eased at `ISO_LOOK_AHEAD_RATE`.

This is the answer to "the camera is still catching up with my body", and it is a better answer than a faster yaw: yaw speed trades smoothness against responsiveness and there is no setting giving both, because they are the same quantity. Look-ahead is a different quantity — the camera shows the space the player is running into *before* it has finished turning to face it, so the octant turn never has to be hurried. **It produces no yaw, structurally**: the offset runs along the camera's own horizontal forward, so camera, follow point and look target share one vertical plane and only pitch can change (measured deviation over 16 bearings × 11 strengths: 8.9e-8 rad, i.e. float epsilon). A cursor-driven yaw is precisely the self-moving rotation the octant model exists to remove and must not return through this door. Measured tilt at full strength: +6.05° at 15 m of zoom, +8.71° at the 10 m near edge, +5.25° at the 17.5 m far edge.

**ISOMETRIC has wall safety of its own** (`_apply_iso_wall_clamp()` → `_update_iso_collision_distance()` / `_probe_iso_camera_distance()`), separate from the TPS occlusion ray. A **sphere** `cast_motion()` runs from the pivot toward the unobstructed camera position along `CollisionLayers.CAMERA_OCCLUSION`; a ray would answer "has the camera's mathematical centre crossed the wall" too late and discontinuously, while a sphere of `ISO_COLLISION_RADIUS` reports the surface a radius early and its answer then varies continuously as the player walks. The probe starts at eye height, not at the follow point — the follow point rides the tracked *ground* height and a probe from there reports a hit on the floor. **Retract is immediate, restore is eased at `ISO_COLLISION_RESTORE_RATE`**: being inside a wall is a correctness failure, being further out than necessary costs nothing, so only the growing direction is smoothed. **The clamp is the last layer, applied to `camera_current_pos` after the position spring** — applied to the target instead, an "immediate" retract is immediate only for the target and the spring then takes its own 0.08 s to carry the camera there, which at `run_speed` 15.5 is longer than the 0.7 m of sphere-plus-margin clearance lasts. It clamps `camera_current_pos` itself rather than only the camera, or the spring would hold a position inside the wall and snap back out to it when the obstruction cleared. Everything upstream decides where the camera *wants* to be; this decides where it may go, and nothing downstream reconsiders — in particular the look target is built before this runs, so a wall changes where the camera is and never where it is aimed. `ISO_COLLISION_MIN_DISTANCE` wins over any wall — the character may be occluded, the camera may not end up inside them. The retracted distance is written to `_iso_effective_distance` and read back by `_build_iso_frame()` so the dead zone keeps its apparent size while pulled in; `current_zoom_distance` is untouched and remains the player's own zoom setting driving the HUD ruler.

The **cursor bias** is gated on distance to the **screen edge**, not on distance from the character (`Frame.cursor_edge_weight`, from `_cursor_edge_weight()`). Nothing at all through the neutral middle `CURSOR_EDGE_DEAD_ZONE` (65%) of the screen, then a smootherstep ramp to full at the edge; the two axes combine as a capped vector, softened a further `CURSOR_EDGE_CORNER_SOFTEN` where both are engaged, so a corner reads 0.75 against an edge midpoint's 1.0 rather than the 1.41 naive independent axes would give. The mouse is also where the player's hand rests while reading the screen, so a bias growing with plain distance made the frame drift for no expressed reason; proximity to the edge asks something they actually mean. **This weights a translation and must not be allowed to weight a yaw** — an ever-present mouse signal driving rotation would reinstate the self-moving yaw the octant model was written to remove, dressed as cursor steering.

That bias takes its ground point by intersecting the cursor ray with a horizontal plane at the follow point's height (`OnFootCameraComponent._cursor_ground_point()`), *not* via `ClickToMoveSystem.raycast_ground_point()`. The camera holds no reference to that system, and a physics hit would be the wrong answer anyway: a move order wants the exact surface clicked, so a discontinuity at a rooftop edge is correct for it, whereas framing needs a value that varies smoothly with the cursor or the camera gets kicked whenever the mouse crosses a parapet. A ray too close to parallel with the ground (`CURSOR_RAY_MIN_DOWNWARD`), or one whose plane hit lands beyond `CURSOR_RAY_MAX_DISTANCE`, does **not** yield "no point" — it yields a synthetic point at `CURSOR_RAY_MAX_DISTANCE` along the ray's ground direction. At the ISOMETRIC pitch the top of the frustum sits about two degrees above horizontal, so the top few percent of the screen is sky and rejecting it was wrong in the one place it costs most: the edge bias ramps *up* toward the edges, so a cursor pushed to the very top would lean the frame nearly all the way and then have it vanish on crossing the horizon — a step in the channel that exists to be smooth, at exactly the gesture it exists to serve. Both consumers want a direction more than a position (the bias saturates its reach, the head-look clamps to a cone), so the synthetic point is the honest answer rather than an approximation.

**The character's head turns in ISOMETRIC**, driven by `OnFootCameraComponent._update_iso_head_look()` through `player.gd`'s `set_head_look_point()`/`clear_head_look_point()`. The rig itself (a `LookAtModifier3D` on the `Head` bone, with its own limits, smoothing and influence fade) already existed in `PlayerAnimationComponent` and had no caller anywhere in the project; only the decision of *where* to point was missing. Priority: an active Q/E glance first (the head turns by exactly the angle the camera leaned, off the body's own facing), then the cursor ground point while the character is stopped — on the move the animation clips drive the head, the same gate the component's own TPS branch applies. Driven from the camera rather than from `player.gd` because both inputs belong to the camera, and `get_camera_yaw()` is not a route to the first: it is fed only by `TpsMovementSystem`, so in ISOMETRIC it holds whatever TPS left behind.

Every branch there yields an **angle off the body's facing**, never a world point, and a single construction at the bottom turns the winning angle into one — that shape is what makes `iso_head_look_limit_deg` (`35.0`, matching the glance limit) unbypassable, with `iso_head_look_cursor_limit_deg` (`25.0`) clamping the cursor tighter still because a glance is asked for and a cursor is not. Handing the cursor's raw world point to the rig let the head turn a full 360°, by two routes: nothing bounded the angle, *and* `PlayerAnimationComponent` lerps the marker's **world position**, so a target jumping front-to-back dragged the marker along a straight line through the character and the look direction swept every angle as it passed the head. A bounded cone at fixed radius fixes both — the interpolation path never comes near the head. One seam is left deliberately: a cursor crossing the line directly behind flips the clamp sign, and the head sweeps across the front rather than through itself.

### Transport (`core/controllers/transport/`)

+`base/hover_base.gd` is the shared hover behaviour (CharacterBody3D pseudo-physics, inertia, yaw smoothing, semi-automatic altitude hold). Control is fed in every frame through `set_move_intent(move, vertical)` — `base/input_hover_controller.gd` (`InputHoverController`) is the player-side implementation and reads exclusively through `InputSystems`. An AI-side controller will use the same interface. Boarding is handled by `hover_entry_trigger.gd` (FSM: `IDLE → BOARDING → SEATED → EXITING`), not by `InteractComponent`. **Both boarding and exiting are hold-to-confirm since 2026-08-28** (`interact_hold_time`, 0.7 s): a press only starts the hold, and the transition runs once at the threshold — `_hold_committed` is what stops a still-held key from firing it again. Getting into a vehicle is the one mis-press in this build that is expensive to undo, and this trigger is the project's only interact claimant, so the hold lives on the claim contract rather than being a general property of interaction.

- Metro, lifts, tube transit and additional hover types are **not implemented** — see `docs/planned_scope.md`. Their placeholder scripts were removed on 2026-07-29.


- **Character physical size** is per-character data (`player/player.gd`'s `body_height` export; `npc/npc_base.gd`'s own) with shared eye/shoulder/chest ratios in `core/characters/body_metrics.gd` (`BodyMetrics`), not duplicated per character. The `Player` `CharacterBody3D` origin sits at the feet. Any value that depends on the character's height (camera framing, raycast origins, attachment points) must go through the `get_eye_height()`/`get_shoulder_height()`/`get_chest_height()` getters — never hardcode a height or assume where origin sits.

- **Player stance** (`PlayerState.stance`, `Stance.PEACE`/`Stance.COMBAT`) is a declared intent, and since H5 equipment is one of the things that can declare it — drawing a weapon IS a declaration, and the point is that it cannot be made quietly. Raised fists are already a statement on their own, which is why the coupling is deliberately asymmetric: entering `COMBAT` never auto-draws, but drawing something whose `readability` is `THREATENING` sets `COMBAT`, and returning to `PEACE` by any route holsters. `player.gd` owns that wiring (`_on_drawn_changed()`/`_on_stance_changed_for_equipment()`) because `EquipmentComponent` knows nothing about stances and `InputSystems` knows nothing about equipment; it is the second-ever caller of `set_stance()`. No loop and no guard flag is needed — `set_stance()` returns early on an unchanged value and `holster()` returns early with empty hands. Mutated only through `PlayerState.set_stance()`, never assigned directly, same rule as `mode`/`view_mode`. Read by `player.gd` (movement speed, TPS body rotation, and — only in `COMBAT`, in both view modes — the punch action on `mouse_left_button`, see `_on_primary_click_pressed()`; ISOMETRIC additionally faces the body to the click point first, via `_face_punch_target()`, since it has no TPS-style camera-driven facing to fall back on. A punch also resolves an **intent target** once at button-accept time — `_acquire_punch_intent()`, a wider-cone/longer-reach reuse of the same `_find_punch_target(reach, angle_deg)` search the hit check runs, stored as an instance id, never a `Node` reference — and `_face_punch_intent()` turns the body toward it for the length of the wind-up, so an NPC that walks out of the cone during `punch_hit_delay` is still swung at. The hit check itself is unchanged, so this improves the odds of a fair punch landing and never guarantees one; the intent clears when the punch ends. A punch that resolves with no target emits `punch_missed(position)` — see the `IdleNPCController` bullet below for its one subscriber, and note it deliberately never reaches `IncidentRegistry`), `core/movement/click_to_move_system.gd` (self-gates off for the whole of `Stance.COMBAT`, on top of its existing `ON_FOOT` + `ISOMETRIC` gate, so click-to-move and the punch never both react to the same `mouse_left_button`/`mouse_right_button` click; stops an in-progress path rather than letting it finish on entering `COMBAT`, since `player.gd`'s navigation branch is keyed on `view_mode` alone and would otherwise keep advancing it), `camera/tps_combat_camera_state.gd` (lock-on gating), `player_animation_component.gd` (a stance-branched AnimationTree — two direction-blended `AnimationNodeBlendSpace2D` branches with identical geometry: a centre/idle point plus seven directional points, forward split into a walk point (`walk_blend_radius`) and a run point (outer edge) since the blend vector's length carries speed; every point is the same clip on both branches except idle, MeleeLib's `LightIdle` for PEACE vs ShooterLib's `sneak-idle` for COMBAT — plus a punch, layered over whichever branch is mixed in via `AnimationNodeOneShot`, ShooterLib's `punch1`), and — as of the drone/NPC work below — the AI decision layer: `idle_npc_controller.gd`'s glance/turn gate still reads `PlayerObservation.stance` (itself sourced from `PlayerState.stance` by `PerceptionComponent`, only when the player is actually seen), but `patrol_drone_controller.gd`'s ALERT no longer does — see the `IncidentRegistry` paragraph below for what replaced it. `ui/hud/stance_indicator/stance_indicator.gd` is the newest consumer — a HUD badge next to the health bar showing PEACE/COMBAT by both colour and text, self-contained like `KeyHintsPanel` (reads `PlayerState.stance`/`stance_changed` directly in `_ready()` rather than through a `WorldContext`). The evidence system still doesn't read stance. Not reset by `open_menu()`/`close_menu()`.
  - **`PlayerState.is_aiming`** is a COMBAT-only modifier, not a third stance (`set_aiming()` silently clamps to `false` outside `Stance.COMBAT`/`Mode.ON_FOOT` — a held aim button crossing a stance change mid-press is ordinary input, not an error). Read by `player.gd` (`aim_speed_multiplier`, stacked on top of the COMBAT speed multiplier), `on_foot_camera_component.gd` (dollies TPS camera distance to `TPS_AIM_DISTANCE`, widens shoulder offset by `aim_shoulder_offset_multiplier` — wins even over an active lock-on), and `ui/hud/aim_reticle/` (a debug-grade screen-centre cross, visible only while aiming — confirms ADS reads on screen, not the final aiming UI).
- **`KeyHintsPanel`** (`ui/hud/player_hud/key_hints_panel.gd`, instanced inside `player_hud.tscn`, H2 — `docs/scope_horizon.md`) shows the actions valid for the player's CURRENT `PlayerState` snapshot (`mode`/`view_mode`/`stance`/`is_aiming`), bottom-center, whenever `InputSystems.key_hints_enabled` is true, laid out as THREE COLUMNS — Movement / Action / System — not one horizontal ribbon: a flat row list only ever encoded meaning through `sort_order`, which the eye can't read at a glance, forcing a full scan every time. `KeyHintEntry.category` (`Category` enum: `MOVEMENT`, `ACTION`, `SYSTEM`) picks the column; column ORDER on screen is the enum's own declaration order (`KeyHintsPanel._build_columns()` iterates `Category.values()`, no case statement choosing order in the panel itself), and within a column rows still sort by `sort_order`. Three, not four: a dedicated camera/view column would only ever hold one or two rows, so those entries live in `ACTION`. A column with zero active rows hides itself (header included), never leaving an empty slot in the `HBoxContainer` of columns. Data-driven from `KeyHintEntry`/`KeyHintsCatalog` (`ui/hud/player_hud/`, populated in `res://data/key_hints.tres` — see the entry below for what's in it) rather than a hardcoded per-state switch — an entry's `modes`/`view_modes`/`stances` arrays are empty for "any", so an action valid everywhere doesn't have to enumerate every enum member. An entry can describe a GROUP of actions that share one meaning (`KeyHintEntry.action_names`, e.g. WASD → one "Move" row) instead of one action each — `get_action_names()` returns `action_names` if set, else the single `action_name`, so an ungrouped entry is unaffected; `get_row_key()` (the joined action names) is what the diffed rebuild tracks a row by, not `action_name` directly, precisely so a group gets one stable row identity. Key labels are resolved live from `InputMap`, never authored by hand, so a rebind cannot make the panel lie: keyboard wins when an action has more than one bound event (none do today), otherwise the first event of whatever else it's bound to; a keyboard event's `as_text()` has any trailing parenthetical stripped, a mouse button becomes LMB/RMB/MMB/MB4/MB5/`MB<n>`, and a wheel tick becomes `Wheel Up`/`Wheel Dn`/`Wheel Left`/`Wheel Right` — spelled out in ASCII rather than drawn with `↑`/`↓`/`←`/`→`, since the key label's font is a bare `SystemFont` request (`_build_mono_font()`) with no guarantee the resolved font actually carries the Arrows Unicode block; unverified hypothesis, not something checked by running the game. A group's per-action labels are joined by `group_key_separator` (one exported value, not repeated per call site). Rebuilds only on `PlayerState`'s four signals, diffed PER COLUMN against the rows already on screen in that column (keyed by `get_row_key()`) rather than cleared and rebuilt wholesale, so an unrelated stance flip doesn't flash rows that are still valid — same diffing shape as before columns existed, just scoped per column's own row list instead of one shared one (`_rebuild_column()`). Self-contained relative to the rest of `player_hud.gd`: reads `PlayerState`/`InputSystems` directly in `_ready()` instead of waiting on `on_world_ready(context)`, since both are autoloads and nothing here needs the player/camera a `WorldContext` would hand over.
  - **`res://data/key_hints.tres`** was trimmed from 39 rows to 22 `KeyHintEntry` resources (movement/camera-pair actions collapsed into grouped rows; `inventory`/`map`/`status` removed outright — those systems don't exist, and a hint promising them is a lie; `toggle_stream_debug`/`toggle_perception_debug` removed as observer-only debug overlays, out of scope for "can a reviewer operate the build"; `toggle_follow`/`toggle_tabs`/`switch_shoulder` removed as low-value secondary camera preferences) so a state shows roughly ten rows instead of forty — the original per-action population proved unreadable on screen. `debug_save`/`debug_load` were briefly one grouped `K / L` row (`"Debug save / load"`) and were split back into two: the paired key label and the paired description didn't unambiguously say which key was which action, and the one row saved wasn't worth that ambiguity. Every entry carries a `category` (`MOVEMENT`/`ACTION`/`SYSTEM`) for its column; `lock_on` was the one genuinely debatable case — filed under `ACTION` (closer to targeting/combat than to `MOVEMENT`) rather than invented a fourth column for it. Actual per-state row counts (three-column layout): ISOMETRIC+PEACE 11, ISOMETRIC+COMBAT 10, TPS+PEACE 11, TPS+COMBAT 12, HOVER 8.
