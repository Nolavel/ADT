# Saving, lodging and identity

The save contract and its implementers, the in-fiction save point, and the stable
actor ids durable records key on.

Split out of `CLAUDE.md` on 2026-08-25 — it had grown to 94 KB with single
paragraphs over 4000 characters, which is a document nobody edits: agents append
to the end instead of correcting the middle, and that is where the repeated drift
came from. The text here is the same text, moved, not rewritten.

`CLAUDE.md` remains authoritative for the rules; this file is authoritative for
the contracts it describes.

---

- **Save contract** (H1, `docs/scope_horizon.md`): `WORLD_SYSTEM_SCRIPTS` entries may implement three methods together — `get_save_key() -> StringName`, `get_save_data() -> Dictionary`, `load_save_data(data: Dictionary) -> void` — the same optional-opt-in idiom as `on_world_ready(context)`, checked with `has_method()`. `get_save_key()` exists because the payload's top-level keys must not be class names (`SaveSystem`'s own rule: renaming a script must not orphan a save file) — each system states its own key explicitly. `get_save_data()`/`load_save_data()` payloads are dictionaries/arrays/primitives only — no `Node`, no `Object`, no scene-instance resource paths. `SaveSystem` (`core/world/save_system/`, a `WORLD_SYSTEM_SCRIPTS` entry, added last) walks `WorldContext.systems` and writes/reads `user://saves/slot_<n>.json` via `save_to_slot(slot)`/`load_from_slot(slot)`, both returning `bool`. The payload's `"version"` field has been present since the very first save this project writes; a save whose version doesn't match is refused outright (`push_warning`, no partial apply), never half-loaded. `SaveSystem` itself knows nothing about lodging, sleeping, lighting, or any other system's meaning — it only moves dictionaries; the decision of *when* to save belongs to whoever is handling the in-fiction save point (`LodgingRoom`, see below — confirming a sleep calls `save_to_slot()` directly). Debug save/load is bound permanently to `debug_save`/`debug_load` (`K`/`L` — originally `F5`/`F9`, rebound 2026-08-12 because `F5` collides with the Godot editor's own "Run Project" shortcut when the game view is embedded; `InputSystems.debug_save_pressed`/`debug_load_pressed`) — a developer tool, not a stand-in for sleeping. The debug handlers additionally log one line per system (`get_save_key()`: size of each array/dict field) after every save/load — `save_to_slot()`/`load_from_slot()` themselves stay silent when called from game logic. Implemented today by `GameClockSystem` (trivial payload — `total_game_hours`), `IncidentRegistry` (hard payload — see above), `LodgingSystem`, and `PlayerPersistenceSystem` (whose own consumers are `InventoryComponent` and `EquipmentComponent`). **`SaveSystem` walks `WorldContext.systems` and nothing else** — it never searches the scene tree — so a component hanging off the player has no route into a save on its own. `PlayerPersistenceSystem` (`core/world/player_persistence/`, a `WORLD_SYSTEM_SCRIPTS` entry) is that route, and deliberately the only one: the contract does not widen, a second system implements it on the player's behalf, because "the player has components" is exactly the in-fiction knowledge `SaveSystem` is kept free of. Its payload nests one level — `{"components": {"<component's own save_key>": {...}}}` — with each component stating its own key under the same rule as the top level. A component opts in the same way a system does, checked through the now-shared `SaveSystem.implements_save_contract()` (promoted from private static specifically so the contract is defined once rather than restated per caller). It walks the player's DIRECT children only, so a future component parenting meshes beneath itself doesn't get them swept in. Unlike `SaveSystem` it cannot abort a bad save — `get_save_data()` has no failure channel — so an empty or duplicate component key is skipped with a `push_error` instead, losing that component rather than the file. `InventoryComponent` is the first consumer: it writes `{id, count}` pairs and resolves them back through `ItemCatalog` on load (which is why that catalog exists), replaces its contents outright rather than merging, deliberately does NOT emit `item_added` per restored stack (nothing was added — same distinction `incidents_restored` draws), drops an id the catalog can't resolve rather than holding a null, and does not re-check `max_carry_weight` on load, since the file is authoritative about what was carried.
- **`ActorBase.actor_id`** (`core/characters/actor_base.gd`, `@export var actor_id: StringName`) is the stable, authored id `IncidentRegistry` keys perpetrators/witnesses on — same authoring convention as `BlockBase.id`/`LodgingRoom.room_id`, deliberately not derived from `get_path()`/`get_instance_id()`, both of which change across a streaming reload. `get_actor_id()` returns it; every `ActorBase` warns once in `_ready()` if left unset. The player is not an `ActorBase` and carries the analogous contract independently — `player.gd`'s `ACTOR_ID` constant (`&"player"`) and its own `get_actor_id()` — so `IncidentRegistry` resolves both through the same duck-typed call.
- **`LodgingSystem`** (`core/world/lodging/`, a `WORLD_SYSTEM_SCRIPTS` entry) is the durable per-room record — same "survives block unloading" reasoning as `IncidentRegistry`, for the same reason (a room's contents can't live on a node that streams out). `get_room_record(room_id)` creates a default record (`last_slept_game_hours: float`, `storage: Array`, the latter unused today) on first access; `notify_slept(room_id, slept_at_game_hours)` records it. `last_slept_game_hours` is an ABSOLUTE `GameClockSystem.total_game_hours` reading, not a duration — "how long ago did I sleep here" needs a clock reading to answer, not the length of the nap — taken by the caller after advancing the clock and passed in; `LodgingSystem` does not resolve `GameClockSystem` itself, since its one caller (`LodgingRoom`) already holds that reference to advance the clock in the first place. `LodgingSystem.NEVER_SLEPT` (`-1.0`) marks an unslept room, distinct from `0.0` (a real, reachable "slept during game hour 0" value). Implements the save contract (`get_save_key()` → `"lodging"`). Deliberately does not know `SaveSystem` exists — the sleep interaction (a `LodgingRoom` scene, `world/lodging/`) is what calls `notify_slept()` and then separately asks `SaveSystem` to write; keeping that a one-way dependency is enforced by this file simply never importing `SaveSystem`.
- **`LodgingRoom`** (`world/lodging/lodging_room.tscn`/`.gd`) is an ordinary scene, never instanced by any of `world.gd`'s three declarative lists — Stan places it by hand into whichever streamed block he chooses (already done once: `world.tscn` carries one instance under `StreamContainer`, `room_id = "1"`). "Lodging", not safehouse or home: nothing in Blackrock belongs to the player, same naming convention as `Hover*` over `Vehicle*`. Node tree: `Geometry` (greybox 8×8 room, `StaticBody3D`s on collision layer `1|2`, one wall split to leave a doorway gap), `PresenceArea` (`Area3D`, answers only "is the player inside" — `_player_inside`, no other logic), `BedPoint` (an ordinary `InteractableObject`, `InteractionType.BUTTON`, through the same `InteractComponent` path every interactable uses — no bespoke input for beds), `HourLabel` (`Label3D`, not in the original node diagram — added because "the selected hour count is visible" and "a refusal is a message, not a silent failure" are both explicit requirements and no reusable HUD/toast system exists anywhere in this project; world-space, not a `CanvasLayer`/`WORLD_UI_SCENES` entry, so the room stays fully self-contained). This is the in-fiction save point H1 exists to prove out: a debug keybind (`SaveSystem`'s `K`/`L`) proves the plumbing, this proves the contract is worth having. Interaction is a picker, not an instant sleep: first `BedPoint` interact opens a `MIN_SLEEP_HOURS..MAX_SLEEP_HOURS` (`1..8`) hour picker (default `8`), `lodging_hours_up`/`lodging_hours_down` (mouse wheel) adjusts it, a second interact confirms, `pause` cancels — same `_selecting`-flag self-gating idiom every other `InputSystems` consumer uses, not a second input path. Confirming does exactly three things, in order: `GameClockSystem.total_game_hours += hours`, `LodgingSystem.notify_slept(room_id, total_game_hours)` (the ABSOLUTE post-jump reading), `SaveSystem.save_to_slot()` — and emits `slept(room_id, hours)`, a seam nothing subscribes to yet (a future health/hunger recovery pass would, not a subscription this file makes on their behalf). Sleeping is refused (a flashed `HourLabel` message, never silent) unless `_player_inside` and `PlayerState.stance == PEACE` — both re-checked continuously while the picker is open (`_on_presence_area_body_exited()`/`_on_stance_changed()` cancel it immediately if either breaks), not just at the moment it opened. Resolves `GameClockSystem`/`LodgingSystem`/`SaveSystem` via `get_tree().get_first_node_in_group()` against a lookup group each carries (`GROUP_GAME_CLOCK`/`GROUP_LODGING_SYSTEM`/`GROUP_SAVE_SYSTEM`), retried every `_process()` until all three succeed — same static-scene-instance situation `PatrolDroneController` is in, and the same fix, not a lighter one: an earlier version assumed a single `_ready()` attempt was enough on the theory that this scene "only exists inside already-streamed content." That assumption depended on placement, which this scene doesn't control — Stan's own first placement put the instance directly in `world.tscn`, not in a streamed block, and Godot's bottom-up `_ready()` ordering meant all three resolves failed there (2026-08-13, see `CHANGELOG.md`). `systems_search_timeout` (`5.0`s) gates a single `push_warning` if any of the three is still missing past that, same idiom as `PatrolDroneController.incident_registry_search_timeout`.
- **`InteractableObject.activated`** (`world/interactables/interactables.gd`) now actually fires. `InteractComponent._activate_button()` (`player/player_components/interact_component/`) was an empty stub — the signal and its doc comment ("doors/lifts/terminals subscribe to this") already existed, but nothing ever emitted it, so `InteractionType.BUTTON` did nothing on interact for any object, ever. Filled in (`current_interactable.activated.emit(player)`), not bypassed — `LodgingRoom`'s `BedPoint` is the first real consumer.
