# Items, equipment and widgets

Item identity, what is worn and held, how equipment becomes visible, and the morph
glyph contract.

Split out of `CLAUDE.md` on 2026-08-25 — it had grown to 94 KB with single
paragraphs over 4000 characters, which is a document nobody edits: agents append
to the end instead of correcting the middle, and that is where the repeated drift
came from. The text here is the same text, moved, not rewritten.

`CLAUDE.md` remains authoritative for the rules; this file is authoritative for
the contracts it describes.

---

- **`ItemCatalog`** (`core/items/item_catalog.gd`, `data/items/catalog.tres`) is the one place an item id resolves to an `ItemResource`. Before it, an item reached the game exactly one way — hand-assigned in the inspector to `InteractableObject`'s own `@export` — and nothing could turn `&"test_can"` back into the resource, so anything that has to STORE an item rather than hold one (a save payload, an equipment slot) had nowhere to go; storing the reference instead is barred by `SaveSystem`'s dictionaries-arrays-primitives rule. Deliberately **not** a `WORLD_SYSTEM_SCRIPTS` entry: `IncidentRegistry` and `ComicEffectSystem` are nodes because they hold runtime state and have a lifecycle, and a catalog is immutable data — a node would buy a group lookup and a lifecycle for nothing. Deliberately **not** reached through an `@export` either: `InventoryComponent` is a scene node and could take one, but `EquipmentComponent`, NPCs and anything `.new()`-built cannot, and an export wired per consumer is what rots — so `ItemCatalog.shared()`/`get_item(id)` are static, the same shape as `MorphIcon.find_in()`. Found by PATH (`CATALOG_PATH`) rather than a `DirAccess` scan, same export-safety trap `ComicEffectSystem` documents. Two lookup forms on purpose: `find(id)` is the silent query ("is there such an item"), `get_item(id)` warns on an id that resolves to nothing, because a caller naming a specific item expects it to exist. A missing catalog warns once and makes every id unresolvable; nothing here is fatal. `ItemResource.id` is a `StringName` as of 2026-08-23 — an identity, the same kind `ActorBase.actor_id` already is (`BlockBase.id` is still a plain `String`; that inconsistency predates this and was left alone) — and `InventoryComponent`'s `take()`/`get_count()` follow. That component still stores the `ItemResource` itself in `_stacks`, so it remains unsaveable as it stands; the ids being resolvable is what makes fixing it possible, not the fix itself.
- **`EquipmentComponent`** (`player/player_components/equipment_component/`, a direct child of `Player` — `PlayerPersistenceSystem` walks direct children only, so it must stay one) is what is worn and what is in its pockets. Holds item **ids**, never `ItemResource` references — a slot holding an object would be unsaveable by construction under `SaveSystem`'s payload rule; `ItemCatalog` resolves an id when the item's traits are actually needed. Two levels, matching the data: body slots come from the `EquipmentLayout` assigned in the inspector, pockets are derived **live** from whatever garments are worn right now (`_find_pocket()` re-derives rather than caching a table, because what is worn changes and a stale pocket table is a bug that hides). `equip()` into an occupied slot **refuses** (`Refusal.SLOT_OCCUPIED`) and never swaps: an implicit swap has to put the old garment somewhere, and a component that knows nothing about inventory could only drop it — silently destroying the player's clothes. `unequip()` refuses while the garment's own pockets still hold something (`POCKETS_NOT_EMPTY`), for the same reason one level down: those pockets leave with the garment. `Refusal` is an enum, not a bool, so a caller can tell the player something true. Implements the save contract (`get_save_key()` → `"equipment"`); `load_save_data()` restores **body slots before pockets** — that order is load-bearing, since a pocket only exists while its garment is worn — and re-validates every entry against the current layout and catalog rather than trusting the file, so a garment removed from the game cannot resurrect as an entry nothing can address. `starter_garment_ids` (jumpsuit + boots) is worn from the first frame: the character starts dressed, there is no undressed baseline. Knows nothing about meshes, bones or stance — those are later steps. `draw(slot_path)`/`holster()`/`get_drawn()` are the third of H5's three states — what is held. A drawn item is REMOVED from its slot and remembers where it came from (`_drawn_from`), so holstering puts it back exactly there: that slot is guaranteed free, whereas `stow_anywhere()` would drop it in a different pocket each time. `ItemResource.can_use_in_hands` gates whether something can be drawn at all; `readability` gates whether drawing it means anything — the two compose, so no invented "is a weapon" flag was needed. Both halves of the drawn state are saved (`drawn`/`drawn_from`); without the second, holstering after a load would have nowhere to put the thing back. `stow_anywhere(item_id)` is the "put this away on the body" entry point: the garment's own body slot if it is a garment, else the first EMPTY pocket that takes it (candidates tested with `can_stow()` so a full jacket doesn't log four refusals on the way to the fifth pocket). A pocket is a socket and holds exactly ONE item regardless of `max_stack` — stacking is `InventoryComponent`'s business.
- **Where a picked-up item ends up** is decided by `player.gd`'s `store_item(item)`, and deliberately not by either component: equipment first, inventory second. `EquipmentComponent` knows nothing about inventory by design, and `InteractComponent` has no business deciding — its job ends at "the player wants this thing". The player owns both components, so the ORDER between them is its decision. `InteractComponent._store_item()` calls it duck-typed through `has_method()` (the same idiom `on_world_ready()`, `get_actor_id()` and the save contract use — `player.gd` carries no `class_name`), and frees the world object only on success; a refusal leaves the item in the world untouched, which is the honest outcome of "there is nowhere to put it".
- **`EquipmentVisualsComponent`** (`player/player_components/equipment_visuals_component/`) makes equipment visible and **reflects state, never owns it** — deleting it must change nothing except what is on screen, which is also the fastest way to prove a bug is not the visuals'. **Equipment is authoritative over the visibility the scene authored**: `refresh_all()` hides every mesh named by any garment in `ItemCatalog` before showing the worn ones, so a garment mesh is visible only because something worn names it. Without that sweep `_apply_body_slot()` could never hide a mesh `player.tscn` had authored `visible = true` — `_slot_meshes` starts empty, and an empty slot returns early before hiding anything — so at frame 0 the scene's own visibility, not the equipment, was the source of truth, and the two agreed only by coincidence. It is also what makes the component observable at all: emptying `EquipmentComponent.starter_garment_ids` in the inspector now actually undresses the character, and dropping just `starter_boots` is a clean discriminator since boots and jumpsuit are separate meshes even though the body is one. Only meshes an item names are swept — `Genesis8Male_Shape`, `Low Poly Headset` and `DETAILS Low Poly` are named by nothing and are never hidden by it. Two mechanisms, deliberately not interchangeable. **Clothing** is a skinned `MeshInstance3D` already in the rig, found by the name `GarmentData.mesh_node_name` gives and toggled `visible`; it deforms with the body because it is skinned to the whole skeleton, where a `BoneAttachment3D` would follow one bone rigidly and trousers would not bend at the knee. **A held item** is a `MeshInstance3D` built under a `BoneAttachment3D` on the hand — rigid, which is right for something that does not bend — from `ItemResource.held_mesh`, a `Mesh` rather than a scene so holding something costs one field instead of a `.tscn` per item; null means the drawn STATE is still correct and nothing shows, which is silent on purpose since most items will be in that position for a long time. **The skeleton is `OriginalSkeleton`, not `GeneralSkeleton`** — the former is the retarget target every visible mesh is actually skinned to, has 65 bones and indexes them differently (`Head` is 5 here and 6 there, `RightHand` is 34 here and 32 there); attaching to the wrong one is the easiest available mistake in this area. `held_offset`/`held_rotation_deg` are `@export` and meant to be dragged in the inspector, the same reasoning `VotiveProjector.bone_local_offset` already carries: a bone's local axes rarely match anything's forward assumption and the values can only be found by looking. `npc.tscn` carries the same rig, the same five mesh names and the same `Head` attachment, so the garment→mesh-name mapping would work on NPCs unchanged — nothing drives it there, because NPCs have no equipment component. Known limitation: the starter jumpsuit occupies `torso` but its mesh covers the legs, so a future separate trouser garment would draw the same shins twice — a consequence of one garment covering two body regions in the art, not of this mapping.
- **Equipment data** (`core/equipment/`, `core/items/`, `data/equipment/`) is H5's slot model as resources, with no component reading it yet. **`ItemTraits`** (`core/items/item_traits.gd`, `RefCounted`, never instantiated — same shape as `CollisionLayers`) holds the two enums an item and a slot both have to speak: `SizeClass` (`POCKET`/`CARRIED`/`BULKY` — three because three is what today's rules need, a pistol must fit a jacket pocket and a rifle must not) and `Readability` (`CONCEALABLE`/`ORDINARY`/`THREATENING` — how the item reads to an observer, the only axis on which "a machine gun on your back gives away your intent" is expressible, and deliberately the smallest slice of the wider item model). They live in their own script rather than on `ItemResource` because `EquipmentSlotDefinition` must name a size class while `ItemResource` reaches `GarmentData` which reaches slot definitions — on `ItemResource` that is a cycle GDScript resolves badly. **`EquipmentSlotDefinition`** describes ONE socket and is used for both a body slot and a pocket, because they are the same thing: `id` (`StringName`, an authored identity like `ActorBase.actor_id`), `max_size`, and `refuses_threatening` (true on `back_unique` alone). A socket, never a grid — no packing, no rotation, no cells. **`EquipmentLayout`** (`data/equipment/player_layout.tres`) answers the "who registers the slots" question that `register_slot()` left open: it is a `Resource` assigned on the character, and it describes the BODY only — `legs`/`torso`/`feet`/`back_pack`/`back_unique`. **Pockets are not in the layout.** Slot count is a property of the garment: **`GarmentData`** (optional `ItemResource.garment` field, null = not a garment, same "unset is a no-op" contract as `NPCBase.archetype`) names the body slot it occupies by id and carries its own `pockets`. That split is what makes clothing replaceable — a different jacket brings a different number of pockets and the character does not change — and it is why concealed carry is granted by the garment: take the jacket off and the pistol's hiding place leaves with it. `data/items/starter_jumpsuit.tres` and `starter_boots.tres` are the first garments; the jumpsuit occupies `torso` and carries all four pockets (two chest, two thigh) because it is one garment covering both, which is also the honest reflection of the rig — there are no separate trouser and jacket meshes yet.
- **`MorphIcon`** (`ui/widgets/morphs/`, `docs/MORPHS_INTEGRATION.md`) is a small spring-driven glyph parented under a `Button`, saying what that widget is doing right now — `Mode` `LINE` (rest) / `WAVE` (noticed) / `CIRCLE` (held). Same base-class-as-contract shape as `ActorBase`: `DragHandleController`, `RevolverHammerController` and `MenuController` hold a `MorphIcon` and never name a concrete morph, so a second glyph is one new script under `ui/widgets/morphs/` and zero controller edits — the reason the type is the base and not `ThreeDotsMorph`. The base owns the `Mode` vocabulary, `to_line()`/`to_wave()`/`to_circle()`/`get_mode()` (all routing through `set_mode()`, so a subclass overrides ONE method and cannot be handed a mode it never saw), and the static `MorphIcon.find_in(host)` lookup that replaced a per-controller `_find_morph()` copy. **A morph is optional everywhere and null is silent, never a warning** — the gesture must work identically with no glyph attached, which is also the fastest way to prove a bug is not the morph's. `ThreeDotsMorph` is the first concrete one (pure `_draw()`, no child nodes); its `auto_hover_wave` must stay `false` wherever a controller owns the glyph, or hover and gesture fight over the same three dots. `SpringPoint` (`RefCounted`) is shared by all morphs and deliberately has no per-morph stiffness knobs — the family is meant to feel like one thing — but does clamp its own step (`MAX_STEP`), because semi-implicit Euler at `DAMPING 22` diverges past ~0.09s and this build has threaded streaming hitches. Controllers drive the glyph from their own `Phase` through `_set_phase()`, which also emits `phase_changed`.
