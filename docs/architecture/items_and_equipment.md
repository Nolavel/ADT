# Items, equipment and widgets

Item identity, what is worn and held, how equipment becomes visible, and the morph
glyph contract.

Split out of `CLAUDE.md` on 2026-08-25 — it had grown to 94 KB with single
paragraphs over 4000 characters, which is a document nobody edits: agents append
to the end instead of correcting the middle, and that is where the repeated drift
came from. The text here is the same text, moved, not rewritten.

`CLAUDE.md` remains authoritative for the rules; this file is authoritative for
the contracts it describes.

---

- **`ItemCatalog`** (`core/items/item_catalog.gd`, `data/items/catalog.tres`) is the one place an item id resolves to an `ItemResource`. Before it, an item reached the game exactly one way — hand-assigned in the inspector to `InteractableObject`'s own `@export` — and nothing could turn `&"test_can"` back into the resource, so anything that has to STORE an item rather than hold one (a save payload, an equipment slot) had nowhere to go; storing the reference instead is barred by `SaveSystem`'s dictionaries-arrays-primitives rule. Deliberately **not** a `WORLD_SYSTEM_SCRIPTS` entry: `IncidentRegistry` and `ComicEffectSystem` are nodes because they hold runtime state and have a lifecycle, and a catalog is immutable data — a node would buy a group lookup and a lifecycle for nothing. Deliberately **not** reached through an `@export` either: `InventoryComponent` is a scene node and could take one, but `EquipmentComponent`, NPCs and anything `.new()`-built cannot, and an export wired per consumer is what rots — so `ItemCatalog.shared()`/`get_item(id)` are static, the same shape as `MorphIcon.find_in()`. Found by PATH (`CATALOG_PATH`) rather than a `DirAccess` scan, same export-safety trap `ComicEffectSystem` documents. Two lookup forms on purpose: `find(id)` is the silent query ("is there such an item"), `get_item(id)` warns on an id that resolves to nothing, because a caller naming a specific item expects it to exist. A missing catalog warns once and makes every id unresolvable; nothing here is fatal. `ItemResource.id` is a `StringName` as of 2026-08-23 — an identity, the same kind `ActorBase.actor_id` already is (`BlockBase.id` is still a plain `String`; that inconsistency predates this and was left alone) — and `InventoryComponent`'s `take()`/`get_count()` follow. That component still stores the `ItemResource` itself in `_stacks`, so it remains unsaveable as it stands; the ids being resolvable is what makes fixing it possible, not the fix itself.
- **`EquipmentComponent`** (`player/player_components/equipment_component/`, a direct child of `Player` — `PlayerPersistenceSystem` walks direct children only, so it must stay one) is what is worn and what is in its pockets. Holds item **ids**, never `ItemResource` references — a slot holding an object would be unsaveable by construction under `SaveSystem`'s payload rule; `ItemCatalog` resolves an id when the item's traits are actually needed. Two levels, matching the data: body slots come from the `EquipmentLayout` assigned in the inspector, pockets are derived **live** from whatever garments are worn right now (`_find_pocket()` re-derives rather than caching a table, because what is worn changes and a stale pocket table is a bug that hides). `equip()` into an occupied slot **refuses** (`Refusal.SLOT_OCCUPIED`) and never swaps: an implicit swap has to put the old garment somewhere, and a component that knows nothing about inventory could only drop it — silently destroying the player's clothes. `unequip()` refuses while the garment's own pockets still hold something (`POCKETS_NOT_EMPTY`), for the same reason one level down: those pockets leave with the garment. `Refusal` is an enum, not a bool, so a caller can tell the player something true. Implements the save contract (`get_save_key()` → `"equipment"`); `load_save_data()` restores **body slots before pockets** — that order is load-bearing, since a pocket only exists while its garment is worn — and re-validates every entry against the current layout and catalog rather than trusting the file, so a garment removed from the game cannot resurrect as an entry nothing can address. `starter_garment_ids` (jumpsuit + boots) is worn from the first frame: the character starts dressed, there is no undressed baseline. Knows nothing about meshes, bones or stance — those are later steps. `draw(slot_path)`/`holster()`/`get_drawn()` are the third of H5's three states — what is held. A drawn item is REMOVED from its slot and remembers where it came from (`_drawn_from`), so holstering puts it back exactly there: that slot is guaranteed free, whereas `stow_anywhere()` would drop it in a different pocket each time. `ItemResource.can_use_in_hands` gates whether something can be drawn at all; `readability` gates whether drawing it means anything — the two compose, so no invented "is a weapon" flag was needed. Both halves of the drawn state are saved (`drawn`/`drawn_from`); without the second, holstering after a load would have nowhere to put the thing back. `stow_anywhere(item_id)` is the "put this away on the body" entry point: the garment's own body slot if it is a garment, else the first EMPTY pocket that takes it (candidates tested with `can_stow()` so a full jacket doesn't log four refusals on the way to the fifth pocket). A pocket is a socket and holds exactly ONE item regardless of `max_stack` — stacking is `InventoryComponent`'s business.
- **Where a picked-up item ends up** is decided by `player.gd`'s `store_item(item)`, and deliberately not by either component: equipment first, inventory second. `EquipmentComponent` knows nothing about inventory by design, and `InteractComponent` has no business deciding — its job ends at "the player wants this thing". The player owns both components, so the ORDER between them is its decision. `InteractComponent._store_item()` calls it duck-typed through `has_method()` (the same idiom `on_world_ready()`, `get_actor_id()` and the save contract use — `player.gd` carries no `class_name`), and frees the world object only on success; a refusal leaves the item in the world untouched, which is the honest outcome of "there is nowhere to put it".
- **`EquipmentVisualsComponent`** (`player/player_components/equipment_visuals_component/`) makes equipment visible and **reflects state, never owns it** — deleting it must change nothing except what is on screen, which is also the fastest way to prove a bug is not the visuals'. **Equipment is authoritative over the visibility the scene authored**: `refresh_all()` hides every mesh named by any garment in `ItemCatalog` before showing the worn ones, so a garment mesh is visible only because something worn names it. Without that sweep `_apply_body_slot()` could never hide a mesh `player.tscn` had authored `visible = true` — `_slot_meshes` starts empty, and an empty slot returns early before hiding anything — so at frame 0 the scene's own visibility, not the equipment, was the source of truth, and the two agreed only by coincidence. It is also what makes the component observable at all: emptying `EquipmentComponent.starter_garment_ids` in the inspector now actually undresses the character, and dropping just `starter_boots` is a clean discriminator since boots and jumpsuit are separate meshes even though the body is one. Only meshes an item names are swept — `Genesis8Male_Shape`, `Low Poly Headset` and `DETAILS Low Poly` are named by nothing and are never hidden by it. Two mechanisms, deliberately not interchangeable. **Clothing** is a skinned `MeshInstance3D` already in the rig, found by the name `GarmentData.mesh_node_name` gives and toggled `visible`; it deforms with the body because it is skinned to the whole skeleton, where a `BoneAttachment3D` would follow one bone rigidly and trousers would not bend at the knee. **A held item** is a `MeshInstance3D` built under a `BoneAttachment3D` on the hand — rigid, which is right for something that does not bend — from `ItemResource.held_mesh`, a `Mesh` rather than a scene so holding something costs one field instead of a `.tscn` per item; null means the drawn STATE is still correct and nothing shows, which is silent on purpose since most items will be in that position for a long time. **The skeleton is `OriginalSkeleton`, not `GeneralSkeleton`** — the former is the retarget target every visible mesh is actually skinned to, has 65 bones and indexes them differently (`Head` is 5 here and 6 there, `RightHand` is 34 here and 32 there); attaching to the wrong one is the easiest available mistake in this area. `held_offset`/`held_rotation_deg` are `@export` and meant to be dragged in the inspector, the same reasoning `VotiveProjector.bone_local_offset` already carries: a bone's local axes rarely match anything's forward assumption and the values can only be found by looking. `npc.tscn` carries the same rig, the same five mesh names and the same `Head` attachment, so the garment→mesh-name mapping would work on NPCs unchanged — nothing drives it there, because NPCs have no equipment component. Known limitation: the starter jumpsuit occupies `torso` but its mesh covers the legs, so a future separate trouser garment would draw the same shins twice — a consequence of one garment covering two body regions in the art, not of this mapping.
- **Equipment data** (`core/equipment/`, `core/items/`, `data/equipment/`) is H5's slot model as resources, with no component reading it yet. **`ItemTraits`** (`core/items/item_traits.gd`, `RefCounted`, never instantiated — same shape as `CollisionLayers`) holds the two enums an item and a slot both have to speak: `SizeClass` (`POCKET`/`CARRIED`/`BULKY` — three because three is what today's rules need, a pistol must fit a jacket pocket and a rifle must not) and `Readability` (`CONCEALABLE`/`ORDINARY`/`THREATENING` — how the item reads to an observer, the only axis on which "a machine gun on your back gives away your intent" is expressible, and deliberately the smallest slice of the wider item model). They live in their own script rather than on `ItemResource` because `EquipmentSlotDefinition` must name a size class while `ItemResource` reaches `GarmentData` which reaches slot definitions — on `ItemResource` that is a cycle GDScript resolves badly. **`EquipmentSlotDefinition`** describes ONE socket and is used for both a body slot and a pocket, because they are the same thing: `id` (`StringName`, an authored identity like `ActorBase.actor_id`), `max_size`, and `refuses_threatening` (true on `back_unique` alone). A socket, never a grid — no packing, no rotation, no cells. **`EquipmentLayout`** (`data/equipment/player_layout.tres`) answers the "who registers the slots" question that `register_slot()` left open: it is a `Resource` assigned on the character, and it describes the BODY only — `legs`/`torso`/`feet`/`back_pack`/`back_unique`. **Pockets are not in the layout.** Slot count is a property of the garment: **`GarmentData`** (optional `ItemResource.garment` field, null = not a garment, same "unset is a no-op" contract as `NPCBase.archetype`) names the body slot it occupies by id and carries its own `pockets`. That split is what makes clothing replaceable — a different jacket brings a different number of pockets and the character does not change — and it is why concealed carry is granted by the garment: take the jacket off and the pistol's hiding place leaves with it. `data/items/starter_jumpsuit.tres` and `starter_boots.tres` are the first garments; the jumpsuit occupies `torso` and carries all four pockets (two chest, two thigh) because it is one garment covering both, which is also the honest reflection of the rig — there are no separate trouser and jacket meshes yet.
- **The world pickup scene** (`world/interactables/carbine/carbine.tscn`, H6 S1–S2 2026-08-26 as the pistol, replaced by the carbine 2026-08-27) is the first object in the project that can actually be picked up — `test_can` and the since-removed `scrap_pipe` existed as `ItemResource`s with nothing in the world holding them, and the only `InteractableObject` instance anywhere was `LodgingRoom`'s `BedPoint`, a `BUTTON`. So this scene is the shape every later pickup copies, and the pieces `InteractableObject` requires are not optional: a `RigidBody3D` root carrying the script, a `MeshInstance3D`, a `CollisionShape3D`, an `Area3D` **named exactly `Area`** and an `InteractiveVisualIndicator` child — the last two are `@onready` lookups by path (`$Area`, `$InteractiveVisualIndicator`) and a rename breaks detection silently. `interaction_type = INVENTORY_ONLY` is what routes the weapon to the body rather than into the hands: that branch calls `player.gd`'s `store_item()` (equipment first, inventory second) and frees the world object only on success. **The indicator does nothing without a texture** — `_ready()` returns early unless `indicator_sprite_texture` is assigned, which is why `BedPoint`'s indicator has never shown anything; the carbine assigns `assets/icons/icon_interactive.png`.
- **A pickup's `Area3D` must reach the player's focus cast, and for anything lying on the ground that means a tall box.** `PlayerFocusCast` is a capsule at y 1.3 with radius 0.4 — it sees roughly 0.9 m to 1.7 m above the feet, and `player.tscn` marks that reach as a deliberate gameplay choice ("Change these numbers on purpose"). An object resting on the terrain sits at ankle height and is simply **outside** that volume, so `on_detected_by_player()` never fires: no tick, `current_interactable` stays null, and the interact key has nothing to act on. The carbine's detection box is therefore `1.0 × 2.4 × 1.0` centred a metre above the object origin, not a snug wrapper around the mesh. The `Area` is what the object offers to be found by; it is not the object's silhouette, and sizing it to the mesh is the mistake that shipped here first. **Since 2026-08-27 that Area is no longer the only route in:** `InteractComponent` runs a second INTENT tier when the focus cast misses — a 2.5 m sphere query in a 240° forward cone over the same layer and the same Areas — so an object needs nothing new to be reachable, and F on a target further than `pickup_distance` walks the character over rather than refusing. The tall box is still right: it is what makes an object on the ground reachable by the *focus* tier, which is the one that acts with no walk at all.
- **A placed pickup is frozen on the instance, not in the scene.** The island is a slope — measured 22° at the spawn area — and a box-shaped `RigidBody3D` on a 22° incline never sleeps: it micro-slides indefinitely and walks away from where it was authored (measured: 2.15 m in the first three seconds, still moving). `freeze = true` is therefore set on the **instance in `world.tscn`**, not in `carbine.tscn`, so the scene stays physical for a future dropped-in-the-world instance while the authored one stays exactly where it was put. Placement height comes from a downward ray against `CollisionLayers.GROUND` plus the mesh's own AABB minimum, not from eyeballing — the ground under the spawn area is Y 128.762 while `world_data.tres`'s `spawn_point` is Y 130.062, so guessing from the spawn value drops the item nearly two metres. **The numbers do not carry over between meshes:** the carbine's AABB minimum is −0.1447 against the pistol's −0.118, so swapping the mesh moved the authored Y from 128.89 to 128.917 — re-measure, never re-use.
- **`held_mesh` takes a single `Mesh`, and a multi-part placeholder is an `ArrayMesh`.** The carbine's receiver/barrel, stock and grip are three `BoxMesh` primitives baked into one `ArrayMesh` with three surfaces (`data/items/meshes/carbine_placeholder.res`, ≈ 4.6 cm × 20 cm × 73 cm), generated once by a throwaway tool and committed as the result. This keeps the contract's "a `Mesh` rather than a scene so holding something costs one field instead of a `.tscn` per item" intact. The barrel runs along **+Z**, matching this project's visual-forward convention, and **the mesh's origin is its grip** — regenerated on 2026-08-27 with every vertex shifted `(0, +0.088, +0.088)` so a zero fit already puts the weapon in the fist rather than holding it by the middle of the barrel. **A two-handed weapon has one attachment and one only:** the held mesh goes to a single grip pivot, so the left hand is placed by whatever the rifle clips already do and the mesh does not track it. A grip that reads wrong there is an animation question, not a fit one.
- **The rig is scaled, so a held mesh needs a pivot that cancels it.** `player.tscn`'s `player_base_mesh` carries a uniform **0.38763407** scale, and it is the only scale between the player and the hand bones. `EquipmentVisualsComponent` used to parent the held mesh straight to `RightHandAttachment`, which meant **every held item in the project rendered at 38.8% of its real size** — a 73 cm carbine as 28 cm — and every offset written for one was silently in skeleton units rather than metres (the pistol's `held_offset` of `0.33` was 12.8 cm). Nothing said a word; it just looked like the numbers needed tuning. The fix is a **`GripPivot` `Node3D` under each hand attachment** carrying the reciprocal scale (**2.5797526**), so everything below it is in world metres. `left_grip_path` exists alongside `right_grip_path`, with a new `LeftHandAttachment` (`LeftHand` is bone 10 of `OriginalSkeleton`, `RightHand` is bone 34). `_check_grip_scale()` warns when a pivot's global scale leaves 1.0 by more than 10% — a loose threshold on purpose, since an animated bone's pose basis runs up to 2% off orthonormal, while the failure being guarded against is off by a factor of 2.6.
- **Where the hand is belongs to the character; how the object sits in it belongs to the object.** The pivot is the first half. The second is **`HeldFit`** (`core/items/held_fit.gd`, optional `ItemResource.held_fit`, the same "unset is a no-op" shape `garment` uses): `hand`, `offset`, `rotation_deg`, `scale`, all in metres. It replaced `EquipmentVisualsComponent.held_offset`/`held_rotation_deg`, which were component-wide — one pose shared by everything ever drawn, tuned against the pistol and inherited by the carbine, which is how a component ends up holding a pose for geometry it knows nothing about. A null fit is not a failure: it means nobody has fitted this item yet and the pivot's own origin is the honest place for it. Deliberately its own `Resource` rather than three fields, because the same shape is wanted again for where a weapon sits while **stowed**, and that should be a second field of this type.
- **`addons/item_fitter/` is how a `HeldFit` is authored.** An `EditorPlugin` dock: pick an `ItemResource`, pick the hand, pick and scrub one of the character's animation clips, drag the mesh with the ordinary 3D gizmo, Save. The preview is a **real node parented to the same `GripPivot` the game uses at runtime**, which is the whole trick — the editor's own gizmo works on it for free, and because the pivot cancels the rig scale the numbers under it are the metres `HeldFit` stores, so nothing here re-implements a transform editor. It is spawned with **`owner = null`**, so it cannot be serialised into the character scene by someone pressing Ctrl+S with the dock open. **Why an addon and not `tools/`:** an `EditorScript` is a one-shot with no UI and no gizmo, and a `world.tscn` debug panel does not exist at edit time — a dock, a live gizmo and surviving a scene switch are what only an `EditorPlugin` provides. The dock knows no item by name; it reads `held_mesh` and writes `HeldFit`, so the next item works without a line changed, and a stowed-pose field would need one more picker. **One hand, not two:** a parallel prototype (`ItemPose`, staged in `tools/for_claude_addon_item_/` and deleted 2026-08-27) reached the same conclusions — the pose belongs on the item, authored visually against a live animation — and went one step further with a second mesh in the off hand carrying its own transform. That step is the recorded next move if the carbine's left hand reads wrong; it is `TODO(equipment)` on `HeldFit.hand`. Its other idea, grip markers on the item, is already answered differently: the carbine mesh's origin **is** its grip. Its numbers do not transfer — that prototype parented to the `BoneAttachment3D` rather than a `GripPivot`, so its transforms are in skeleton units against the old mesh origin, which is exactly the 38.8% scale bug.
- **`stow_anywhere()` chooses where, and the caller does not get a say.** Three passes, in this order: a garment's own body slot, then the first EMPTY pocket that takes it, then the first empty body slot that `accepts_non_garment`. There is deliberately no "preferred slot" argument. Pockets before the body is what keeps a can off the character's back while a pocket is free, so only what no pocket takes ever gets there. The consequence for the draw animation is unchanged: the gesture follows the slot the item actually landed in (`player.gd._draw_clip_for_slot()`), rather than the item being forced into a slot chosen to suit a clip.

- **Firing is `ItemResource.ranged_damage`, and nothing else.** Zero means the item is not a firearm; a positive number is both the fact and the amount. `readability` cannot answer the question — a melee weapon is `THREATENING` and `can_use_in_hands` just as a firearm is (the starter scrap pipe, since removed, was the worked example) — and this file's own "no invented is-a-weapon flag was needed" was written about **drawing**, which genuinely needed none. There is no bool beside the number, because a flag and a number can disagree. Range is deliberately NOT on the item: `player.gd`'s `shot_range` sits next to `punch_reach`, since how far someone can reach belongs to whoever is holding the thing. `player.gd._drawn_firearm()` is the single place the question is asked. **The carbine is lethal in one shot by that number alone** — `ranged_damage = 150.0` against a default `max_health` of 100 — and by nothing else: `NPCBase._update_knockdown()` already enters a terminal `DOWN` phase the moment `_is_health_depleted()` is true and never leaves it, so "they get back up after being shot" was a damage number, not a missing state. Deliberately above 100 rather than exactly 100, so a tougher NPC later changes this number and not the mechanism.
- **Weapon gestures share one clip node and get their own one-shot.** `PlayerAnimationComponent` carries a second `AnimationNodeOneShot` (`weapon_oneshot`) chained after the punch's, feeding `death_transition`'s `alive` input, with one `weapon_clip` whose `animation` is rewritten immediately before each `play_weapon_gesture()`. Two one-shots rather than one because `is_punch_active()` and `is_weapon_gesture_active()` are what `player.gd` polls to decide when to hand movement back, and a shared node would make the two questions indistinguishable; one clip node rather than three because draw, holster and fire are mutually exclusive uses of the same hands. **Which draw clip plays is chosen from `EquipmentComponent.get_drawn_from()`**, not by forcing the item into a chosen slot — `stow_anywhere()` picks the first empty pocket by design, and a firearm is meant to end up in a jacket's chest pocket once jackets exist. Carrying substitutes `ANIM_COMBAT_IDLE_PISTOL` into the COMBAT blend space's centre point (`set_drawn_idle()`) and leaves all eight directional points alone; a live `AnimationNodeAnimation.animation` write is picked up by a running `AnimationTree` — verified, not assumed.
- **The held mesh waits for the hand, and re-checks before it appears.** `EquipmentVisualsComponent.draw_attach_delay` holds the attach for roughly a third of the draw clip so the item arrives as the hand reaches the pocket, then confirms the same item is still drawn before building — without that re-check a quick draw-then-holster leaves a mesh floating in an empty hand a fifth of a second later. The delay lives here rather than on `player.gd` because "when does the mesh show" is a presentation question; putting the number in both files is the duplication this project keeps paying for elsewhere.
- **Line of sight for a shot is shoulder-to-shoulder, and this is not interchangeable with chest.** `player.gd._has_clear_shot()` casts one ray against `CollisionLayers.SIGHT` between the two characters' `get_shoulder_height()` landmarks. The player carries all three body landmarks; **`NPCBase` exposes only eye and shoulder**, so an earlier chest-to-chest version failed silently on every shot — the missing call took the whole check down and every shot read as blocked, including across open sea. Target selection is separate and reuses `_find_punch_target(reach, angle_deg)` at range with a narrow angle, because NPC bodies carry no collision layer a ray could select on without inventing one; the ray only ever answers "is there a wall". Note for anyone testing this: **tower silhouettes sit on `CollisionLayers.WALL`**, so a character standing inside a generated block's footprint has no clear line to anything — correct for the mask, and surprising the first time it bites.

- **A magazine is `ItemResource.magazine_size` on the item and a count on the character.** Zero means the weapon does not feed from a magazine — the same "zero means it does not apply" shape `ranged_damage` uses one paragraph up. The running count lives on **`WeaponComponent`** (`player/player_components/weapon_component/`, a direct child of `Player`, `{item_id: rounds}`), and it cannot live anywhere else: an `ItemResource` is shared, so a count on it would be one count for every carbine in the game, and `EquipmentComponent`'s own header limits it to what is worn and held — it stores ids and knows nothing that differs between two identical items. A weapon asked about for the first time reports **full**, which is what makes a single found weapon playable. The round is spent at the trigger (`player.gd._try_spend_round()`), not at `_resolve_shot()`: a shot fired is a round gone whether or not it finds anyone. **An empty magazine refuses the whole shot** — no gesture, no damage, no incident — because there is no dry-fire clip in the libraries and a gesture that does nothing reads as a miss. **The reserve is the second number** (`ItemResource.reserve_capacity`, 80 on the carbine; `WeaponComponent._reserves` alongside `_magazines`, seeded the same way): `reload()` moves `min(missing, reserve)` and a partial reload is a success, since refusing one would strand the last rounds permanently. It is finite and nothing restores it — when it reaches zero the weapon is spent, and the answer then is an ammunition pickup, not a bigger number. **`can_reload()` is asked before the gesture starts, not after it ends:** `player.gd` locks movement at the key press and only reaches `reload()` a second into the clip, so without it a full reload animation plays for a weapon with nothing to load — the same lie the empty magazine already refuses to tell on the firing side. `ammo_changed` carries magazine, capacity and reserve together, so a reload that moves two numbers is still one edge. It is on the player's direct children, so `PlayerPersistenceSystem` saves it with no further wiring.
- **A gesture reads as nothing when it is short and from the wrong pack.** Fire and reload were ShooterLib clips (`new4/shoot-rifle-light`, 0.25 s; `new4/reload-rifle`, 1.62 s) while the idle and all eight locomotion points come from the `new3/` rifle pack — a quarter-second snap to a different pack's rifle pose and back is a twitch, and a reload that demonstrably refilled the magazine still looked like nothing happened. Both moved to the same pack as the locomotion: **`new3/rifle_shot`** (1.17 s) and **`new3/rifle_reload_2`** (1.88 s). Both are **non-looping, and that decides the choice as much as the length does** — a looping clip under an `AnimationNodeOneShot` can fail to terminate, and `player.gd` hands movement back on the gesture ending, so a looping fire clip locks the character where it stands. That rules out every shorter candidate: `new3/rifle_fire` (0.57 s) and `new4/shoot-rifle-heavy` (0.42 s) are both imported as looping. `weapon_oneshot`'s `fadein_time`/`fadeout_time` are set explicitly (0.05 / 0.1) rather than left at a default, since a fade is a fraction of the clip and these gestures range from a 0.33 s draw to a 1.88 s reload.
- **Carrying a long gun changes the whole locomotion, not just the idle.** `PlayerAnimationComponent` builds a **third** `BlendSpace2D` (`weapon`) with the same eight-point geometry as `peace`/`combat`, filled from the rifle pack (`new3/rifle_locomotion_run_*` plus `new3/rifle_new_idle` at the centre), and chains it after `stance_blend` on a second `Blend2` (`weapon_blend`). Chained rather than folded into the combat branch because what is in the hands and what stance the character is in are independent questions — a drawn torch is not COMBAT. `set_weapon_locomotion(bool)` is driven from `player.gd`'s `drawn_changed` subscription; it replaced `set_drawn_idle(bool)`, which substituted one clip at the combat centre point and left the eight directional points empty-handed, so a character sprinted with a weapon out as if it were not there. **Two honest gaps:** the pack has one forward clip where the geometry splits forward into a walk point and a run point, so a walk reads as a run with the weapon out; and the pack's `backward_left`/`backward_right` have no point to go to, since no stance in this project has rear diagonals.
- **A body slot can hold something that is not clothing, and only because it says so.** `EquipmentSlotDefinition.accepts_non_garment` is true on `back_pack` and `back_unique` and nowhere else. `max_size` cannot answer this on its own — `legs`/`torso`/`feet` are `CARRIED`-sized too, and a carbine strapped to a leg is not what that slot means. Without the flag a long gun has no legal place on the body at all: it is `CARRIED`, so no pocket takes it, and body slots used to be garments-only, which would make a picked-up carbine instantly unstorable. `refuses_threatening` still applies on top and is what decides between the two: an automatic `stow_anywhere()` puts the carbine in `back_pack`, never on `back_unique`, so the slot that puts its contents on open display still takes a deliberate act. **The draw cycle walks these slots too** (`player.gd._drawable_slot_paths()`, pockets first) — walking pockets alone made the only weapon in the game unreachable by the key that exists to reach it, which is the scrap-pipe failure from the other direction.
- **`HoldPrompt`** (`ui/widgets/hold_prompt/`, a `WORLD_3D_ENTITY_SCENES` entry since 2026-09-02) is the key prompt: a tapered plate with the letter `F`, standing over whatever it was shown for, morphing `F → ○ → ●` as a hold progresses. **It is in the world, not on the glass.** It was a `Control` on the UI canvas that unprojected its anchor every frame, which drew it at a constant pixel size however far away the object was. The same Control and the same `_draw()` now render into a **`SubViewport`** whose texture is carried by a billboarded **`Sprite3D`** at the anchor — perspective scale and real placement come with that, and so does an entrance that is TRAVEL rather than a fade: the badge rises out of the ground decal (`seated_offset` → `risen_offset`, growing from `seated_scale`) and sinks back into it, which is what makes the marker and the letter read as one affordance. **Always on top** (`no_depth_test`), Stan's call: the prompt is a statement the game is making, not an object in the scene, and a depth-tested badge at chest height is lost behind the player's own shoulder constantly. Two things about the plumbing are load-bearing — the `Control` stays **visible for its whole life** and the *billboard* is what appears and disappears (a hidden Control renders nothing into the viewport, so the sprite would carry a blank frame exactly while fading out), and the viewport's `render_target_update_mode` follows that visibility so a 220×220 target is not redrawn every frame between pickups. It **decides nothing** — no inventory, no `store_item()`, no threshold — and is found by group (`GROUP_HOLD_PROMPT`) the way `ComicEffectSystem` is, because `HoverEntryTrigger` is a static scene instance that never receives a `WorldContext`. Delete the node and every interaction still works. Two details are load-bearing: `set_progress()` is a **target** the widget eases toward (rising fast so a commit never lands before the dot is drawn, falling slowly so a cancelled hold rolls back with no caller animating it), and `instant_complete()` **locks the panel up** for ~0.24 s — a pickup frees the world object, so `InteractComponent` reports "nothing targeted" on the very next frame and the tap payoff would otherwise never be drawn. `InteractComponent` asks it to show or hide every physics frame rather than on the `interact_target_changed` edge, because the other half of the condition — `InputSystems.is_interact_claimed()` — changes without the target changing; the widget ignores a repeat show for the same node, so the entrance still plays once per candidate.

- **The prompt and the decal are ONE affordance and are driven the same way** (2026-09-02). `HUDComponent`'s candidate decal used to come from the `interact_target_changed` EDGE while the panel came from a per-frame call, and that asymmetry was a bug: anything that hid the decal won permanently, with no edge left to raise it again — reproduced as the F panel over the lodging bed with no decal under it after walking past a hover door. Both are now re-asserted every physics frame, and `HUDComponent` **reads** `InteractComponent` (`current_interactable`, `is_target_in_reach()`) rather than being pushed by it, so what finds things still does not know who draws them. `TargetIndicator`'s show/hide are idempotent against an in-flight transition for the same reason — `_disappear()` used to leave `is_visible_indicator` true for the length of its fade, which under per-frame assertion built one tween per frame.

- **The affordance has THREE phases, and the reach test is what sequences them** (2026-09-03). Far (a target inside `intent_radius`, further than `pickup_distance`): the tick sprite floats over the object and knocks, the ground decal is dim, and `HoldPrompt` is **down**. In reach: the tick lifts away and the badge rises out of the decal in its place, decal bright. Lost: both leave, the tick with the same lift. Before this, `_update_affordance()` raised the badge on `current_interactable != null` with no distance test at all, so from 2.5 m the tick and the F plate were up together and physically overlapped — measured on a render frame at 2.00 m, the tick sits inside the plate. The missing piece was an event: `on_detected_by_player()`/`on_lost_by_player()` both fire on a change of TARGET, and walking up to something already targeted is neither, so `InteractableObject.on_reach_changed(in_reach)` is the third one, called from `_emit_target_if_changed()`'s existing edge filter and reusing the indicator's own two entrances. It deliberately leaves `is_detected` alone: the object is still detected, only nearer. **The cost is real and deliberate** — F is now hidden from 2 m even though pressing it there works (`try_interact()` walks the character over); the tick carries that half of the message.

- **"Silent while the key is claimed" means SILENT, not hidden.** `InteractComponent` used to call `hide_prompt()` on every claimed frame, stomping the panel the claim holder had raised one frame earlier — which is why a hover door showed nothing at all however long the player stood in it (measured 2026-09-02). A claim owns the display as well as the key: `HoverEntryTrigger` raises both halves on ARRIVAL, not on the first press, and places the decal through `HUDComponent.show_candidate_at()`, found by `GROUP_HUD_COMPONENT`.

- **The press has a payoff.** A tap used to run the morph in the idle white with the glyph not turning, because `_holding` was only ever set by the hold path. `instant_complete()` and `set_holding(true)` now punch the plate inward (`PRESS_PUNCH`), flip the register to active, spin the glyph while the morph runs, and the finished dot throws an expanding ring (`_draw_commit_burst()`). The punch rides the same `pulse` scalar every drawn element already reads, so plate, glyph, ring and dot compress together rather than one of them jumping alone.

- **The pickup gesture is chosen by height, not by `interaction_type`.** `InteractComponent` says only that a pickup succeeded and where the object was; `player.gd.play_pickup_gesture()` compares that against the player's own origin (its feet) and `pickup_ground_height` (0.6 m) to pick `new4/pickup_item` (crouch and take) or `new4/interact-button` (reach out). Height because the question is literally where the hands have to go, and a can on a table is not a button. Movement is deliberately **not** locked, unlike a punch or a shot: reaching for a thing is not a commitment. The gesture shares `weapon_oneshot` with draw/holster/fire/reload — they are the same hands and cannot both be doing something.
- **The draw key cycles, and it is the only way to choose what is in your hands.** `player.gd._on_draw_holster_pressed()` (bound to `Tab`) steps through the drawable items on the body — `get_available_pockets()` order first, then the back body slots: empty hands draw the first, pressing again holsters and draws the next, the press after the last leaves the hands empty. It used to draw the *first* drawable, which is only ever correct when there is one — the starter scrap pipe sat in an earlier pocket than a picked-up pistol, so the key produced the pipe every time and the pistol was unreachable. **Deliberately no ranking** (no "prefer a firearm"): which of two things you want in your hand is a decision, and a hierarchy in code has to be renegotiated with every third item. **The hands are checked before the pocket list** — a drawn item is in no pocket, so with one weapon the list is empty while it is held, and testing "is there anything to draw" first silently refuses to holster.
- **`starter_stowed_ids` must not carry a second drawable** while the cycle is the only selection mechanism. It is empty for that reason; a starter garment or a non-drawable trinket is still fine to author there.

- **`MorphIcon`** (`ui/widgets/morphs/`, `docs/MORPHS_INTEGRATION.md`) is a small spring-driven glyph parented under a `Button`, saying what that widget is doing right now — `Mode` `LINE` (rest) / `WAVE` (noticed) / `CIRCLE` (held). Same base-class-as-contract shape as `ActorBase`: `DragHandleController`, `RevolverHammerController` and `MenuController` hold a `MorphIcon` and never name a concrete morph, so a second glyph is one new script under `ui/widgets/morphs/` and zero controller edits — the reason the type is the base and not `ThreeDotsMorph`. The base owns the `Mode` vocabulary, `to_line()`/`to_wave()`/`to_circle()`/`get_mode()` (all routing through `set_mode()`, so a subclass overrides ONE method and cannot be handed a mode it never saw), and the static `MorphIcon.find_in(host)` lookup that replaced a per-controller `_find_morph()` copy. **A morph is optional everywhere and null is silent, never a warning** — the gesture must work identically with no glyph attached, which is also the fastest way to prove a bug is not the morph's. `ThreeDotsMorph` is the first concrete one (pure `_draw()`, no child nodes); its `auto_hover_wave` must stay `false` wherever a controller owns the glyph, or hover and gesture fight over the same three dots. `SpringPoint` (`RefCounted`) is shared by all morphs and deliberately has no per-morph stiffness knobs — the family is meant to feel like one thing — but does clamp its own step (`MAX_STEP`), because semi-implicit Euler at `DAMPING 22` diverges past ~0.09s and this build has threaded streaming hitches. Controllers drive the glyph from their own `Phase` through `_set_phase()`, which also emits `phase_changed`.
